# Hexu 业务共识

Hexu 起始基线｜2026-10-01｜业务规则唯一正文；依据用户最新说明及此前确认的需求。

<a id="b01"></a>
## B01｜服务对象与登录即用

面向同时存在纯软与软硬件开发的企业团队，解决 AI 使用水平不一、过程分散和交接困难。普通成员登录 Web 即可工作，不必安装个人 AI 软件或自行配置模型。管理员、环境负责人仍需完成必要准备。

<a id="b02"></a>
## B02｜任务先讨论，确认后才开发

一个任务承载一个持续目标及其多轮沟通，不是每句话新建一张卡。想法尚不成熟时，任务就在所属项目内以“待开发（讨论中）”保存，AI 协助澄清需求、比较想法、补充细节和整理可行方案；可以持续讨论，不要求立即排入开发。

| 阶段 | 业务含义 |
| --- | --- |
| 待开发（讨论中） | 不启动实际开发，不修改代码、运行开发作业或操作硬件。讨论服务不以开发主机在线为前提。 |
| 待执行 | 用户确认目标、细节和本轮交付要求后，由有执行权限的成员将任务拖入此状态；这一步是从需求讨论转为授权代码开发的入口，并非首次启用 Pi。 |
| 开发中 | Pi 已实际开始获授权的工作；任务保留进度与过程。仅排队不算开发中，缺少环境或预算时说明等待原因。 |
| 待验收 | 交付后返回此状态，先呈现简要总结：做了什么、验证结果、未解决事项及成果入口。 |
| 已完成 | 人类正式接受本轮结果；评论反馈及后续处理见 B09。 |

“待处理”统一称为“待执行”，不另增状态。创建任务、讨论充分或 AI 建议“可以开始”，都不能代替用户转入待执行；转入后也不要求员工另行启动个人 AI 客户端。

开发使用用户已确认的需求与相关讨论结论，而非仅任务标题。等待、中断和取消须说明真实原因，不能假装开发中或已完成。

<a id="b03"></a>
## B03｜项目内共同可见、共同评论

同一项目的所有成员都能看到该项目全部阶段的任务，包括尚在讨论的任务，并能在任务卡下发表评论、补充资料和参与协作；不限定为创建人或被分配人。

项目负责人组织目标、粗计划、分工和依赖。成员可以接力，也可由一人组织多项 AI 工作；项目的相关资料和结论可共同借鉴，子任务完成后仍需整体检查。

可见与评论权不等于执行、取消或最终验收权；执行与取消由获授权成员操作，最终验收由指定验收负责人完成。非项目成员不得访问；成员退出后撤销访问。平台管理员不因管理平台就自动取得业务资料权限。

<a id="b04"></a>
## B04｜两类环境，保留原有习惯

平台可登记多个共享或专用环境。纯软工作使用共享开发主机；软硬件工作允许批准注册工程师现有电脑，保留代码位置、IDE、工具链、许可证及硬件连接。Web 发起任务，本地工具仍可用于调试；具体环境选择与切换办法待交接确认。

注册只开放批准的项目和操作，不开放整台电脑的私人内容。保护工程师已有修改；人与 AI 对同一内容的修改发生冲突时，先暂停、隔离或取得确认，不覆盖、不静默混入人工工作。

<a id="b05"></a>
## B05｜有边界地持续工作

已获授权且环境在线的开发不因关闭浏览器或员工下班而停止。主机关机、休眠、断线或设备不可用时，应说明等待或中断；不得擅自换机器继续，也不得在恢复后重复已有操作。

需要插线、实物观察或危险操作时等待有资格的人。取消须反映下游工作是否真正停止；无法立即停止时明确提示并保留后续结果与费用记录。

<a id="b06"></a>
## B06｜平台统一提供 AI

讨论和代码开发都由同一套后端 Pi 处理；平台按任务阶段提供相应的 skills（技能）与工作侧重。

| 阶段 | 主要角色 | 工作重点 |
| --- | --- | --- |
| 待开发（讨论中） | 需求分析师／项目经理 | 梳理想法、澄清需求、评估可行性、形成计划。 |
| 进入开发阶段 | 开发工程师／软件架构师 | 依据已确认需求完成设计、代码实现、验证与交付。 |

平台统一提供 Pi 环境、模型接入和密钥；阶段变化不要求用户更换 AI 工具或重新讲述背景。技能与角色变化不自动扩大允许操作范围，开发入口仍遵循 B02。

<a id="b07"></a>
## B07｜按任务选模型，按结果看成本

后台结合难度、风险、可用能力和预算选择模型：低风险简单工作考虑经济路线，困难或高风险工作采用更适合的能力。没有合适能力时说明限制，不擅自降低要求，也不承诺总能选到最优模型。

讨论与实际开发的用量都应有记录；“未执行开发”不等于“没有 AI 消耗”。费用包含必要的重试与返工，不重复计费，不把未知费用当成零。评价的是被接受成果的总成本，不只是单次调用价格。

<a id="b08"></a>
## B08｜过程可追溯，方法可复用

任务保留需求、必要的对话、关键决定、工作记录、产物和反馈。负责人从待验收、缺信息、阻塞或反复返工进入依据；接手者获得相关背景，而非一句“继续做”。

经确认的有效方法可形成共享模板或专家能力；共享方法不自动共享其他项目的历史、资料和凭据。反馈用于改善流程，不以用量、聊天长度或单一评分给员工排名。

<a id="b09"></a>
## B09｜评论驱动反馈，不绕过状态与责任

待验收后，人类看简要总结，在同一任务的评论中反馈：有验收权的人明确接受结果（如“已完成”），可据此记录验收并将任务置为已完成；提出修改或下一步需求，则先明确范围，确认后回到待执行进入下一轮。尚未成熟的新想法可回到待开发继续讨论，旧讨论和交付结果保留。

普通意见、疑问、被引用的“已完成”或“还没完成”，不等于正式验收。含义不明确时先澄清；无验收权成员的评论仍保留为意见，不能直接结束任务。

开发中也允许成员评论。评论须被记录和处理，但不自动另开并行开发或悄悄改变已确认范围；范围变化先明确本轮或下一轮如何处理。已完成任务收到新评论也不自动重启开发。

<a id="b10"></a>
## B10｜单人可维护，能力可独立调整

本项目由一人开发维护，以真实使用和反馈推进。保留有价值成果、复用适用能力；各能力职责清楚，调整模型、专家方法或环境时，不应破坏任务协作、权限、历史和验收。

需求不由开源项目的功能清单决定；具体取舍见 [来源与取舍](source-notes.md)，实施范围及未定项见 [验收](acceptance.md)。

<a id="b11"></a>
## B11｜专家团队代为组织工作

2026-10-05 补充：团队成员不必是 AI 应用高手，也不必会编排工作流。成员在任务中说明目标、补充信息、确认关键决定；平台根据阶段与工作类型推荐可复用的团队工作方法，并由协调专家组织所需的分析、规划、实现、检查等角色。工作方法包含角色分工、顺序、输入输出和检查要求，不只是几个角色名字或提示词的集合。简单工作不强制多人协作。

用户面对的仍是同一任务及其讨论，不必逐个启动、选模型或管理子 Agent。团队使用同一套 Pi 能力，按职责配备必要技能；执行过程归入当前任务，提供简要进展、待决定问题、各角色结果和验证依据。项目内可见范围沿用 B03；需要独立分工与验收的工作再形成明确的子任务，不能把每次内部派工都变成用户必须管理的新任务。

团队方法不能跨过 B02 的开发入口：待开发阶段只协助梳理，不因自动规划或角色派发开始改代码；确认转待执行后才允许在批准范围内开发。审查专家的认可不等于 B09 的人类验收。范围扩大、额外授权和现场硬件操作仍按原规则处理。

所有角色共同受同一次任务授权、项目资料范围和 B07 的费用边界约束；方法共享不带出其他项目历史或凭据。团队中有失败、未完成检查或相互矛盾的结论时，汇总必须说明，不以多数赞同掩盖问题；取消、离线与恢复遵循 B05，不能只停止协调者就宣称全部停止。

新增插件是实现上述能力的候选，不成为普通成员的新安装或配置负担。具体来源、建议方法与取舍只在 [来源评估](source-notes.md#pi-herdr-agents) 维护。
